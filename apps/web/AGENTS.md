# Agent rules for the site

Read the root `AGENTS.md` first. Run these commands in this folder, `apps/web/`, or from anywhere with `mise //apps/web:<task>`.

- `npm run check` is the fast default: Biome, the type check, the workflow and lane script tests and Node filesystem/repository guards, including the unchanged use-case guard, plus all six cheap in-process Vite guards (measured together at 1.62 seconds). `npm test` and `test:watch` select both `repository` and `vite-integration`; `test:vite` is a focused subset of that default. Costly stages are explicit opt-ins: `test:browser` (Chromium/WebKit, zones and touch), `test:integration` (guards plus Vite and all browser projects), `test:server` and `test:e2e`. The Vite and browser commands need no `.env.test` or database. Every browser runs in the shared browser server (`compose.browsers.yml`, Docker), which `test:browser`, `test:integration` and `test:playwright` start, so pages render alike on macOS and Linux; the fast default needs neither Docker nor browsers. A fast pass is not evidence for unrun browser/server/e2e stages. Keep timeouts, concurrency and assertions unchanged; optimize or isolate costly tasks to an authorized stage. The orchestrator provides `.env.test` with its database and `E2E_PORT` pinned to the lane. For a manual run, `npm run test-env:init` writes `.env.test` with this worktree's own database and site port (one database per worktree), keeping any existing file; or copy `.env.test.example` by hand. Missing files are errors; test commands never create/copy/rewrite them or allocate their own environment. Different concurrent runs need distinct lanes or manual configurations. Lane resources are reused, not dropped at a command's exit.
- `npm run test:e2e` runs `npm run test:server` followed by `npm run test:playwright`, only when server tests pass. Both use the supplied environment. `npm run test:playwright -- <file>` runs just that e2e file without server tests; provision/migrate its database first. Tests and check must pass; a flake is a failure (`flakes-are-failures`). Keep only one full web suite scheduled at a time until #475 is accepted and operator setup is separately compatible. Merging these scripts does not configure or install pipeline lane-slot wiring.
- Every use case in `use-cases/` has a test or `describe` titled exactly its slug, wherever that test lives. A change in behaviour updates the use case and its test.
- Playwright e2e tests cover only the auth workflows (`e2e-auth-only`). The auth workflows are sign-up, sign-in, sign-out, the sign-in limits, and the signed-out access gate, where a signed-out visitor, or one whose session has lapsed, is sent to log in. Every other case is tested in Vitest:
  - A case that needs a real server or database gets a server test against the test database. It calls the Server Action, route handler or store with real users and sessions, not through a browser.
  - A case that needs only the UI gets a browser-mode component integration or feature-entrypoint test in `test/` (`*.browser.test.tsx`). It need not cover a whole application flow.
- A server test is a `test/**/*.server.test.ts` file. `npm run test:server` loads `.env.test`, resets and migrates its configured local database, then runs tests in Node (`vitest.server.config.mts`). It leaves the database and proxy provisioned. `test:e2e` runs it first; `npm test` and `npm run check` never do, so need no database. Each test makes what it needs with the kit in `test/test-database/`, and `vitest.server-setup.ts` deletes that data after each test:
  - A server test titled exactly by a `use_case_*` slug covers that case; other server tests keep plain titles. No new e2e test covers a case outside the auth workflows.
  - In server tests, share read-only set-up in `beforeAll`, and run independent set-up and reads together with `Promise.all`, but never memory edits or other writes whose order matters. Each `tutorReply`, `tutorPrompt` or `tutorEdits` is a full `POST /api/chat` round trip, so send only the ones an assertion needs. Don't use `/mock-slow` unless the case is about a slow reply. `SERVER_TEST_TIMEOUT_MS` in `vitest.server.config.mts` is there so a busy machine fails no test on timing, not as a budget to fill.
- `use-cases/use-cases.test.ts` enforces `e2e-auth-only` against the auth cases in `use-cases/auth-cases.ts`: an e2e test titled by any other case, or inside a group titled by one, fails it, and so does an entry of the list that isn't a case. `e2e/fixtures.ts` makes its accounts and data with the server tests' kit in `test/test-database/`, `testUser()` and `testData(user)`.

## Test database and port

The orchestrator supplies `.env.test` with a local database and `E2E_PORT` pinned to its lane. Test commands consume that file without allocating a database or port or tearing down lane resources. Manual runs use the file `npm run test-env:init` writes, or one configured by hand, with a distinct database and site port for each concurrent run. Environment settings override `.env.test`.

`checkTestEnvironment()` in `scripts/test-db/test-database.ts` requires localhost or 127.0.0.1, a safe database name, the mock tutor and file outbox before database changes. `test:server` resets and migrates the supplied database; it leaves the database and proxy provisioned.
