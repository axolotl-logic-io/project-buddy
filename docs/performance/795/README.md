## Artifact privacy

Only synthetic Home traces retain screenshot events. Cold-direct filmstrips cover the full document window. Client filmstrips start only after the destination URL is Home, an atlas is visibly rendered, and two explicit rendering frames have completed. That delayed pixel start omits the source and earliest transition frames; the numeric observer still covers reset-before-activation through content presence +2 s. Each traced record stores its screenshot scope and pixel start; sample 1 is traced identically in both variants, while later numeric samples omit tracing. Quest/editor filmstrips and the complete transition windows also use numeric region rectangles without page pixels or user text. This limits the visual evidence deliberately: editor screenshots could contain definition prompts, so they are never captured. Trace events otherwise retain timing/category fields only, without event arguments. Numeric records contain safe region enums, tags, rectangles, booleans and timing values; they contain no prompts, input text, account identifiers, headers, cookies or session data. Artifacts are compressed before sharing.

The first before-sample Home transition traces initially started screenshot capture on the Quests source page. That violated the intended Home-only pixel scope even though the destination trace name was allowlisted. All 14 screenshot events that could include the source page were removed: five desktop frames and nine phone frames. Other trace events and numeric observations are unchanged. The corrected recipe excludes source pixels and starts any Home client pixel trace only after the visibly rendered destination and two rendering frames. This is a recorded capture-policy correction, not a performance rerun.

## Snapshot topology correction

The first checkpoint used flat temporary app snapshots (`before-app/.next`). The baseline editor answered HTTP 200 and then terminated its response before a main landmark or textarea arrived. Four readiness captures failed and a separate diagnostic confirmed no main, no textarea, no busy region and the expected templated route. An authenticated document-only diagnostic independently retained the transport failure. No product fix or passing retry is inferred from those failures.

Inspection found that the production Turbopack runtime resolves filesystem modules relative to a compiled project root three directories above `.next`, matching the original `apps/web/.next` topology. A flat snapshot changed that root to `/tmp`; Markdown dependencies loaded by the editor can therefore resolve filesystem assets outside the preserved project. Corrected snapshots preserve `before-app/apps/web/.next` and `after-app/apps/web/.next`, with the root `node_modules` symlink, app-level config/public files and the app directory as the server's working directory. Document verification passed before the corrected cohort: the editor returned a complete HTTP 200 body with main, textarea and title, and Home returned a complete HTTP 200 body with main, title and atlas. This confirmed the snapshot setup defect without a product change. The earlier records remain a separate checkpoint and will not be pooled into the corrected cohort.

The corrected client-navigation protocol also confirms source hydration through the shared menu: a trusted click must open its dialog, Escape must close it, and the expanded state must become false. These states are awaited directly, without source-readiness sleeps. The observer resets only after that preparation and the link's safe-region scroll. Destination `performance.timeOrigin` must equal the prepared source value; a full-document fallback fails a client-navigation observation. The original checkpoint did not prove that condition, so it remains exploratory evidence only.
