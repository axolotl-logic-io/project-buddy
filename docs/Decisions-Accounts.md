# Decisions: Accounts, quota and releases

Part of [Decisions](Decisions.md). Each decision has a name, which issues and code comments use to refer to it.

## `admin-email-invitations`

New accounts require an invitation sent by an admin from the signed-in site (Axlog, 2026-10-20; #494). This supersedes the shared `INVITE_CODE` sign-up gate and the earlier decisions rejecting per-person single-use invitations, an admin page and a seeded account. The former `/signup` URL explains invitations and offers normal sign-in; neither it nor a direct submission of the old shared code can create an account or send email.

- **Initial admin:** migration 0013 adds `users.role`, defaulting to ordinary `user`, and provisions `me@modestprogress.com` as `admin` if absent, or promotes its existing normalized account by updating only its role. It creates no session. Ownership must still be proved through ordinary emailed-link sign-in. Other accounts and all existing private data are unchanged. The migration is additive/expand-only and compatible with the preceding build; it drops or renames nothing.
- **Admin scope:** invitation administration only, not access to other users' private data or role management. Account shows an Invitations link only to admins. Both `/invitations` and its Server Action recheck the current stored session epoch and role: ordinary users are refused as not found, and signed-out, expired or revoked sessions redirect to sign-in. Unauthorized requests issue no invitation and send no email.
- **Sending:** the admin enters one valid email address. Existing trim-and-lowercase normalization applies. A new address receives a direct `/setup?token=…` link; no account or recipient session is created yet. An existing address receives a normal sign-in link instead, without changing its account, role, projects, chats or settings. Admin sends report storage and email-service failures and allow retry; confirmation means the service accepted the message, not guaranteed inbox delivery. Public sign-in retains its separate privacy response and limits.
- **Setup:** a minimal confirmation page identifies the fixed invited address. GET is read-only, so mail scanners do not consume the invitation or create a session. One POST creates an ordinary account for the stored email, consumes the invitation and signs the recipient in at home. It requires no shared code, password, email re-entry, profile fields or second email. A submitted recipient field cannot reassign the token; the server reads only the token.
- **Lifetime and reuse:** invitation tokens are cryptographically random, stored only as SHA-256 hashes, and work on any device for strictly less than 30 minutes. Missing, malformed, unknown, altered, expired, replaced and already-used tokens grant no account or session. Their page explains that the invitation is unusable, offers normal sign-in for an existing account, and directs an unregistered recipient to ask an admin for a new invitation.
- **Exactly once:** `src/accounts/invitations.ts` atomically deletes the active invitation and inserts its account in one SQL statement. Concurrent confirmations can return only one account/session grant; a storage error rolls consumption and insertion back together. The unique normalized account email also prevents a duplicate account if another invitation or account creation races it. These tokens are separate from reusable normal login links.
- **Replacement and delivery:** an invitation candidate is saved before sending, but is not usable until the email service accepts the send and its active pointer is saved. One active invitation per normalized address means a successful resend replaces the old link with a fresh lifetime. A rejected email leaves the previous link usable; an undelivered candidate cannot be accepted. A failure activating a delivered link is reported as failure, not success, and the admin can retry.
- **Coverage:** isolated-database tests exercise bootstrap provisioning and promotion, account preservation, session/role authorization (including a role revoked after sign-in), validation, fixed recipients, read-only opening, exact expiry, concurrent acceptance, replacement, pending and rejected sends, acceptance during a replacement send, and legacy sign-up refusal. A scratch-database test forces an account insert to fail after claiming an invitation and verifies that consumption rolls back, allowing exactly one successful retry. Expiry tests control issuance times rather than depending on database or delivery speed. Unit tests cover storage failures and setup UI; auth e2e covers the emailed setup flow across browsers, ordinary-user refusal and existing-account login. Invitations and setup have visual baselines and phone checks.

Out of scope: additional seeded admins and a role-management UI. Rejected: one shared code, unbound bearer invitations that can choose their recipient, and a second email exchange to finish setup.

## `passphrase-gated-email-sign-in`

The name is kept for existing references. The sign-up gate it once described, a shared passphrase and then a shared invite code, is superseded by [`admin-email-invitations`](#admin-email-invitations). Normal passwordless sign-in stands:

- **Sign-in** is by an emailed link for an existing account, with no passwords. A link lasts 30 minutes and works any number of times within that window (Axlog, 2026-10-12). The link opens a "Continue" page and only its POST sets the session, so mail scanners never get one. It isn't bound to the browser.
- **Answers never reveal accounts:** the form always says "check your email", including for unknown addresses and rate-limited requests, and the email is sent in `after()` so the timing is equal. Unknown addresses receive no email and create no account.
- **Link limits** (orchestrator, 2026-10-12): 3 per address and connection per 15 minutes; 10 per address per 15 minutes, counting only requests within their connection's limit; 20 per connection per hour. Addresses are stored as HMACs, and expired rows are deleted as limits are counted. No single connection can use up another's links to an address, but many connections together can still fill an address's limit; the use case documents this.
- **Session:** 30 days, in a signed cookie carrying the user's `session_epoch`. **Sign out everywhere** bumps the epoch and deletes the user's login links (Axlog, 2026-10-12). Afterwards an old cookie still gets each page's empty shell before the redirect to `/login`, since `proxy.ts` checks only the cookie's signature and every data read checks the epoch; this stays (Axlog, 2026-10-13; issue #55). Rejected: an epoch check in `proxy.ts`, a database read on every request.
- **Own code, no auth library** (orchestrator, 2026-10-12): Better Auth makes normal links single-use with no way to turn it off, and Auth.js v5 was still beta and deleted tokens on use. Invitations intentionally use a separate single-use flow.

## `resend-for-email`

Resend sends the login and invitation emails (Axlog, 2026-10-11) from the address in `EMAIL_FROM_ADDRESS`, with Hippy, the default buddy, as the display name (#242; `EMAIL_SENDER_COPY` in `src/ui/copy/site.ts`). The sender's domain has Resend's DKIM, SPF and MX records and a DMARC `p=none`; the key is send-only. Calls use plain `fetch` with a zod-checked response, and errors are classified by status and name. In tests, `EMAIL_TRANSPORT=outbox` writes each email to a file instead: to a temporary name unique to the write, then renamed to `<key>.json`, so a reader never sees half a file (orchestrator, 2026-10-12). Rejected: one shared temporary name, and retrying parses in the reader.

## `private-user-data`

Each user's projects, memory, chats and personas are private, with isolation tested between two users. `user_id` is on `projects` and `buddies`, and on `chats` only for a chat in no project; other chats, messages and memory reach their owner through the project. `src/accounts/owner-scope.ts` holds the only ownership predicates, every store function takes `owner` first, and a foreign id reads as not found (orchestrator, 2026-10-12). Rejected: `user_id` on every table, branded owned-id types, and Postgres row-level security (the Neon HTTP driver would need a batch per query).
- **Central chat** (#299, #308, #315, #444): a central (standalone) chat is in no project, so `chats.user_id` names its owner. Exactly one of `chats.project_id` and `chats.user_id` is set (the `chats_one_owner` check). A user can have many central chats: migration 0012 made `chats_user_id_idx` a plain index. `chatOwnedBy` matches a chat whose `user_id` is the owner's or whose project is the owner's, and `messageOwnedBy` follows it. `getChat` returns a union keyed by `kind` (`"project"` or `"central"`). `createCentralChat` and `listCentralChats` (`src/chats/central-chat.ts`) make a new central chat and list the owner's, newest first. Rejected: a separate `central_chats` table, which would split every chat, message and ownership query in two; and a separate getter for a central chat, which would make every caller that looks a chat up by id try two getters.
- **All-chat query** (#479): `listAllChats(owner, projectId?)` in `src/chats/all-chats.ts` reads every owned chat, across projects and no-project conversations, ordered by `createdAt` descending and then `id` descending. It uses `chatOwnedBy` and the existing `FoundChat` conversion used by `getChat`; joins and row conversion stay in the chat stores. Project results include the project's name and interview-chat status; central results have neither a `projectId` nor a `projectName` property.

  An owned project filter restricts the list to that project. A foreign or nonexistent project, or an owned project with no chats, returns `[]`, without falling back to all chats or creating a conversation. An owner with no chats also receives `[]`. No page uses the query yet (#472); URL parsing and invalid-URL fallback belong to the page, not this query.
- **Coverage test** (orchestrator, 2026-10-12): `owner-scope-coverage.test.ts` checks every export of every module that touches user data. An insert passes when the owner is in the inserted values or comes through a parent row the same call inserted for the owner. `login-links.ts` is included, each export allowed by name with its reason, and a stale allowance fails the test. Rate-limit accounting stays out, since it is keyed by address or connection, never a user. Authentication export allowances, including the invitation store, live in `test/accounts/account-owner-scope-test-kit.ts`: sending is admin-authorized and exposes no private account data; reading and accepting a setup token must work before sign-in. Rejected: leaving `login-links.ts` out.
- **A foreign project's memory:** `editMemory` returns `undefined`, as restoring does, and the `update_memory` tool throws `AppError("not-found")` (orchestrator, 2026-10-12). Rejected: a new tool output status, and a `not-found` result variant.
- **Hidden extras** are stored in `users.hidden_extras`. `/settings` writes both the database and the cookie, and sign-in copies the database into the cookie, because the pre-paint script reads only the cookie. Both hold the extras the user has switched away from their default, not the hidden ones (2026-10-14, issue #104), so a flag off by default stays hidden for a user who saved a choice before it existed. The column and the `hidden-extras` cookie kept their names to avoid a migration.

## `account-owned-prompt-choices`

The default-on `brainstorming` and `project-breakdown` switches (issue #483) reuse the existing `users.hidden_extras` account feature choices. Despite the historical column/cookie name, these values record switches away from defaults, not a list of currently hidden controls. Missing new choices therefore leave both skills enabled for existing accounts, including accounts with older saved extras. No migration is needed and older extras retain their meaning.

Settings writes the account and presentation cookie; sign-in seeds the cookie from the account. Unlike display-only extras, planning instructions are selected from the **actual owner's account for each reply and generated opening**, not from the cookie. The owner's name and saved switches are read together. This covers both project-creation interview openings and new-chat lesson openings, as well as project and standalone replies.

The shared prompt prefix depends on the supplied buddy parts and current account preferences. Requests do not reuse an application-cached name or choice from a previous owner. This does not add sharing of private custom buddies or bypass existing chat/buddy ownership checks. Disabled instructions remain in buddy templates and chat snapshots, so re-enabling supplies the captured text, not a replacement default or a later buddy edit. See [buddy planning skills](Decisions-Personas.md#buddy-planning-skills).

Rejected: a presentation cookie authorizing model instructions, per-buddy account preferences, deleting disabled text, or treating the switches as model capability restrictions. Existing extras other than these two skills remain display-only.

## `claude-spend-quota`

Each user may spend $5 of Claude per calendar month in UTC, Axlog included (Axlog, 2026-10-11).
- **What counts:** every model call (replies and every step, the answer-now call, openings, naming) at the model's prices, including cache reads and writes, metered once in `model.ts`. Prices live in `src/quota/prices.ts`, in micro-USD.
- **Over quota:** new messages, chats and projects are refused with the quota message and the reset date (the 1st of next month, UTC), which the server sends. Reading, renaming and editing memory still work. A reply that crosses the line finishes, with its answer-now call and naming. No smaller model is offered. Rejected: allowing new chats over quota.
- **One gate:** a model is made only from the `QuotaGrant` that `checkQuota` in `quota.ts` returns within the quota, so a new model caller can't skip the check (issue #28). Only `quota.ts` and the unit tests' `quota-test-kit.ts` may make a grant (`quota-grant.ts`, held to that by its test), with no type cast outside tests, and only tests and other test kits may import a test kit. The answer-now call and naming reuse the reply's grant rather than checking again. The central chat's `create_project` tool starts a new project, so it checks the quota again, through `startProject`, rather than reusing the reply's grant (#310). Rejected: each caller remembering to call `checkQuota`.
- **A refused send** puts the user's text back in the box and leaves no unsaved message or empty reply behind, including in an empty chat.
- **Usage** shows on the account page, with spend rounded up to the cent, but never shown as the limit itself before the quota is used up: 4,990,001 µ$ shows $4.99, and 1 µ$ shows $0.01 (orchestrator, 2026-10-12). Rejected: rounding down. `formatResetDay` in `quota-terms.ts` is the only reset-day formatter.
- **`out-of-credits`** copy speaks to invited users (the tutor is unavailable, try later), not to an admin.
- **An answered message is never answered again:** a resend gets 409 `already-answered`, which the browser handles by reloading. `saveMessage` reports `inserted` or `already-saved`, and a message saved but missing from the history the request read is also refused (orchestrator, 2026-10-12). A resend that arrives while the first reply still streams is refused the same way (issue #51): a message's `reply_started_at` marks the request that is replying to it. `saveMessage` sets it when it inserts the message, a resend of a held last message must win `claimReply` (one conditional `UPDATE`, so of two at once only one wins), and the reply releases it when it fails, isn't saved, or fails before streaming, so a retry after a fast failure is answered at once. A saved reply keeps its marker, since the reply already answers the message. A marker older than `REPLY_CLAIM_SECONDS` (300 s, the chat route's `maxDuration`) has lapsed, so a function stopped mid-reply can't hold the message forever (orchestrator, 2026-10-13). Rejected: answering a held last message again only after 300 s even when its reply failed, which would block a real retry after a fast failure.
- **An old build reloads on a case name it doesn't know** (issue #63): during a deploy, a browser on the previous build can get a case only the new build has, such as a new quota refusal. Text in a case name's form that names no case it knows (`isUnrecognisedCaseName` in `app-error.ts`), in a chat failure or an error boundary's digest, reloads the page once to pick up the new build. A reload stamp in session storage holds back another for a minute, so a page that still doesn't know the case shows the unknown message instead of looping (`newer-build-reload.ts`). Rejected: reloading on any unknown failure (a network error would lose the page, and a real unknown would loop), and Vercel Skew Protection (hosting configuration, not code). No e2e test, since a mid-deploy version skew can't be staged.
- **Spend for a deleted owner is dropped quietly,** matched only by a foreign-key violation on `monthly_spend`'s user key (orchestrator, 2026-10-12). Rejected: test teardown waiting for `after()`.
- **`finish` waits for the spend write,** so spend is stored before the response ends (orchestrator, 2026-10-12).
- **Month ends in quota tests:** quota tests cover a run that crosses a UTC month's end by seeding next month's spend too, and topping it up after a reply that crosses the quota (issue #56). Server tests seed with `spend` and `spendInMonthAfter` from `test/test-database/spend-test-kit.ts`, and accept either reset day through its `resetDaysSince` and `quotaMessage` (#347). That kit is the one module that holds this knowledge for every test: the account page's visual spec (`e2e/visual/account.spec.ts`) seeds its spend with the same `spend` (#351). Rejected: an injected server clock, which changes production code for a test.
- **A spend write is retried while the database is unreachable** (issue #23): `recordSpend` tries the upsert up to 3 times, waiting 100 ms and then 400 ms, before `finish` passes on, so a brief outage after a reply doesn't lose its cost. Only an unreachable database is retried; a query Postgres rejects fails at once, and a deleted owner's spend is still dropped. A write that committed but whose answer was lost can be counted twice; that is accepted because it errs toward the quota, never past it. Rejected: a durable outbox or idempotency ledger for spend writes (it needs a schema change).
- **Known gaps:** concurrent replies can overshoot $5 by the replies in flight, and a stream stopped before `finish` is charged an estimate (both by design). A spend write still unreachable after its retries is logged and lost.

## `release-workflow`

Production releases are manual (Axlog, 2026-10-13 and 2026-10-14; #74, #148). `.github/workflows/release.yml` releases `main`'s head, triggered by a `deploy` issue from someone with write access or by `workflow_dispatch`. The issue pipeline doesn't work deploy tickets. Neither pushes nor Vercel Git deployments release the site. No build runs migrations.

The workflow runs these steps in order:
1. Build on Vercel with the production environment but no production domain (`vercel deploy --prod --skip-domain`), and wait for READY.
2. Run `drizzle-kit migrate` against `PRODUCTION_DATABASE_URL`.
3. Promote through Vercel's REST API (`.github/scripts/vercel-promote.sh`), then wait up to five minutes for the production domain to serve that deployment.
4. Run signed-out smoke requests with `scripts/release/smoke.ts`.

A failed build or migration leaves the previous build live. **A failed promotion after migration leaves the old code on the new schema and may break production.** The failure report names the deployment. To recover, use a personal Vercel login to run `vercel promote DEPLOYMENT --scope SCOPE`, then run `node scripts/release/smoke.ts PRODUCTION_URL` from `apps/web/`, or fix forward. Replace the placeholders with the reported deployment, project scope and production URL. A rollback restores code, never the schema. Every migration must therefore work with the live build: expand first, contract only in a later release after the live code stops using the old form. Two merges may ship together, so the contract change must not merge into `integration` until the expand release is live.

Release safeguards:
- `concurrency: production-release` prevents overlap. Build has a 25-minute timeout, promotion 10 minutes, and migration and smoke 5 minutes each, below the job's 60-minute limit, so failures are reported rather than silently cancelled.
- Success comments on and closes the deploy ticket; failure comments there and opens or updates `Production release failed: <short sha>`, labelled `ops`. Cancelled steps are reported too. Matching by title avoids duplicate issues if the label is removed. The bot author, not the `ops` label, keeps these issues out of the pipeline.
- Vercel deployment lookup and promotion use REST scripts. The workflow token cannot run CLI commands that look up its user (`inspect`, `promote`, `rollback`, `whoami`, `ls`); `build` and `deploy` work (#151, #239). The CLI version is pinned in `package.json`.
- `test/release-config.test.ts` checks release boundaries and disallowed CLI commands; `.github/scripts/vercel-promote.test.sh` tests promotion with a stand-in curl.

Rejected: migrations during the production build, after promotion, on pipeline merge or at app startup; and automatic releases on every push. These approaches hide failures, expose new code to the old schema, miss manual merges or race cold starts. A release costs about 3–5 Actions minutes.

## `integration-branch`

Every PR merges into `integration`, not `main` (Axlog, 2026-10-14; PR #150). `main` is what production runs, and only `scripts/deploy.sh` moves it. Each push to `integration` starts `.github/workflows/integration.yml`, which builds a Vercel preview (`vercel deploy`, Preview environment) and runs the release's smoke test against it. The preview sits behind Vercel's Deployment Protection, so the smoke test sends the project's automation bypass secret (`VERCEL_AUTOMATION_BYPASS_SECRET`, a repo secret). A failed preview opens, or comments on, an `ops` issue titled `Integration preview failed: <short sha>`. The workflow never migrates, because previews share the production database, so a preview of code that needs a pending migration can fail on the pages that read it. It never promotes either; `test/release-config.test.ts` checks both. A newer push cancels an older preview, which also saves Vercel's 100 deployments a day.

`scripts/deploy.sh [--dry-run] [--yes] [<commit>]` releases a tested commit, the head of `integration` unless another is named. It checks that the commit is on `integration`, that its Integration preview passed, and that `main` fast-forwards to it. It lists what will ship, fast-forwards `main` (never a force-push), and opens a deploy ticket, which starts `release-workflow`. `release.yml` always checks out `main`. A fix pushed straight to `main` must be merged back into `integration` before the next deploy, or the script stops.

`main` stays the default branch, so the release workflow's code and its production secrets come only from `main`, which only a deploy moves. GitHub closes an issue from "Closes #N" only when the PR merges into the default branch, so the issue pipeline closes the issue itself after it merges a PR into `integration`. Releasing is never part of an issue's work. The two steps of an expand-then-contract migration still need separate releases: don't merge the second into `integration` until the first is live. Rejected: making `integration` the default branch (an `issues` event runs the default branch's workflow file, so `integration` code would run the production release).
