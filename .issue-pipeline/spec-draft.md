Sync and checks resume at their own stage.
- `git patch-id --stable` ignores ALL whitespace (man page; I checked it: an indentation change kept the same id). `git patch-id --verbatim` keeps whitespace and implies the stable algorithm (git builtin/patch-id.c: "verbatim implies stable"; https://raw.githubusercontent.com/git/git/master/builtin/patch-id.c). `--stable --verbatim` together is an error. The output is "<id> 0000…0", and empty input prints nothing. A clean rebase onto a base that changed an unrelated line keeps the verbatim id (checked).

## Decisions (put them in the spec's Design and Assumptions)
1. Patch id = `git diff --binary <merge-base(from, head)> <head> | git patch-id --verbatim`, first field. `from` = `measureFrom(stackedOn, cfg)` (stack.ts:209), so it's origin/<base>, or the prerequisite's head when stacked. It's null on an empty diff, a missing merge base or any git failure. **Departure from the issue's `--stable`**: `--stable` would let a whitespace edit (Python or YAML indentation) keep the review, which breaks Behaviour 3. State it as an assumption.
2. New helper, a stub now: `patchIdOf(dir: string, from: string, head: string): string | null` in src/git-state.ts. Its body throws `not implemented (#394)`.
3. prepare-review (ops/sync.ts:141) replies `patchId: string | null` for `baseSha..headSha`. **sync-base is not changed** (departure from triage note 5). In a sweep, the review is never re-run after a sync. Acceptance's own prepare-review gives the patch id at the head it would judge, and that also covers a CI fix after the sync, which would leave a sync-time id stale.
4. State fields: `reviewedPatchId`, `acceptedSha`, `acceptedPatchId` (string|null). Add them to the state.ts zod schema and newState (null), and to workflow/types.ts.
5. Record `reviewedPatchId` from that stage's prepare-review reply (through `carry`, per `stage-carry`) only on a pass: review.ts `reviewed()` with no blocking findings (~213), rereview.ts `settle()` when no finding is open (~138), ci-fix.ts `reviewed()` save (~216). Paths with findings leave it unchanged. Not in accept.ts:144 or security.ts:212.
6. Accept stage (accept.ts `review` phase): after finalDiffOf, if the reply's patchId is a non-empty string === `acceptedPatchId`, run no session. Set stage = "security" and log `acceptance kept: changes unchanged since <acceptedSha 12>`, with the same text in a PR comment, then doneStep like a pass. Otherwise launch the verifier with carry {patchId}. A pass records acceptedSha = verifiedSha and acceptedPatchId = the carried patchId (or null). A fail clears both to null. checks.passed is unchanged (testsOnly still goes to merge; otherwise accept). Departure from triage note 5 (skip in checks.passed): this mirrors security-work? and the wiki's `accept-work?` row.
7. Restart: `StartContext.patchId: string | null`. claim-state.ts `claimedState` fetches the base and the branch into the clone, then calls `patchIdOf(clone, measureFrom(stackedOn,cfg), remote)`, or null when remote is null. `reviewStands` = existing conditions, with (remote === reviewedSha OR patchId non-empty === reviewedPatchId). When it stands by patch id with a moved head, the restart log entry includes `review kept: changes unchanged since <reviewedSha first 12>`. resumedStage: a stop at sync or checks resumes there. A stop at accept, security or merge **with a moved head** (remote ≠ verifiedSha) resumes at checks. branchStart → sync. carriedReview also carries reviewedPatchId, acceptedSha and acceptedPatchId. keptReview (going back to review) resets all three to null. reviewedSha stays as it is (it's the re-review sinceSha). Update the resume-stage.ts comment and the README row (README.md:13). That's the implementer's job, since spec writers change only tests, stubs and wiki.
8. Security: no change. Test that the chain checks(passed, not testsOnly) → accept (skipped by patch id) → security with a different headTree launches the security session. The testsOnly merge case stays as it is.
